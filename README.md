# Лабораторная № 1: защищённое REST API

Учебное API заметок для дисциплины «Информационная безопасность». Три метода демонстрируют JWT-аутентификацию, BCrypt, защиту от SQL-инъекций и экранирование пользовательских данных. Проект использует Java 21, Spring Boot 4.1, Maven и файловую H2.

## Запуск

Нужны JDK 21 и доступ к Maven Central при первой сборке. На Windows в PowerShell:

```powershell
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-21'
$env:LAB1_JWT_SECRET = [guid]::NewGuid().ToString('N') + [guid]::NewGuid().ToString('N')
$env:LAB1_DEMO_ALICE_PASSWORD = 'AliceDemo2026!'
$env:LAB1_DEMO_BOB_PASSWORD = 'BobDemo2026!'
$env:SPRING_PROFILES_ACTIVE = 'demo'
.\mvnw.cmd spring-boot:run
```

Замените `JAVA_HOME` на путь к установленному JDK 21. Пароли в примере относятся только к локальной демонстрации. На Linux/macOS задайте те же переменные окружения и запустите `./mvnw spring-boot:run`. Приложение слушает `http://127.0.0.1:8080`.

Профиль `demo` при первом запуске создаёт пользователей `alice` и `bob`, сохраняя только BCrypt-хэши. Их пароли берутся из переменных окружения. При следующих запусках существующие записи не перезаписываются: если поменять переменные паролей, старые хэши останутся в БД. Для чистой демонстрации остановите приложение и удалите локальный файл `data/lab1.mv.db`. Этот файл игнорируется Git.

H2 работает в файловом режиме и сохраняет заметки после перезапуска. Схему таблиц для этой учебной работы обновляет Hibernate (`ddl-auto=update`). Консоль H2 отключена.

## API

| Метод | Путь | Доступ | Ответ |
|---|---|---|---|
| `POST` | `/auth/login` | открытый | `200` и `{ "accessToken": "...", "tokenType": "Bearer" }` |
| `GET` | `/api/data` | Bearer JWT | `200` и массив собственных заметок |
| `POST` | `/api/data` | Bearer JWT | `201` и созданная заметка |

Вход принимает `{"username":"alice","password":"..."}`. Создание заметки принимает `{"title":"Заголовок","content":"Текст"}`. В защищённых запросах передайте заголовок `Authorization: Bearer <accessToken>`. Ответ заметки содержит `id`, `title`, `content`, `createdAt`. Клиент не передаёт владельца: он определяется по проверенному JWT. Пустые и слишком длинные поля отклоняются с `400`.

Ошибки используют один формат:

```json
{"code":"VALIDATION_ERROR","message":"Некорректные данные запроса","fieldErrors":{"title":"не должно быть пустым"}}
```

Без токена, с поддельным токеном или неверными учётными данными сервер возвращает `401`. Сообщение о неверных учётных данных одинаково для неизвестного логина и неправильного пароля.

## Демонстрация в Postman

Импортируйте [`postman/lab1.postman_collection.json`](postman/lab1.postman_collection.json) и [`postman/local.postman_environment.json`](postman/local.postman_environment.json). Выберите окружение и заполните `alicePassword` и `bobPassword` теми значениями, с которыми создавались пользователи. Запускайте запросы коллекции по порядку. После входа токен сохраняется в переменную коллекции автоматически; в экспортированных файлах паролей и действующих токенов нет.

Коллекция проверяет успешный и неуспешный вход, отсутствие и подделку JWT, создание и чтение заметки, изоляцию данных `alice`/`bob`, попытку SQL-инъекции, XSS-строку и ошибку валидации. Для повторной демонстрации входа `alice` после запроса 09 запустите запрос 01 ещё раз.

## Как устроена защита

- **SQLi:** `UserRepository.findByUsername` и `NoteRepository.findAllByOwnerIdOrderByCreatedAtDesc` используют связанные параметры Hibernate. Введённые строки не конкатенируются с SQL/JPQL.
- **XSS:** введённые `title` и `content` сохраняются как данные и экранируются через `HtmlUtils.htmlEscape` при создании response DTO. Это экранирование для текстового HTML-контекста; браузерный клиент всё равно должен вставлять значения как текст и учитывать контекст HTML, JavaScript, CSS или URL.
- **Аутентификация:** пароли хэшируются BCrypt. После входа сервер выдаёт JWT на 15 минут; Spring Security Resource Server проверяет HS256-подпись, `exp`, `iss` и `aud` в цепочке фильтров. Секрет должен содержать минимум 32 байта UTF-8 и поступает из `LAB1_JWT_SECRET`.
- **Доступ:** заметки выбираются по ID пользователя из JWT. Приложение слушает только loopback-интерфейс. API не использует сессии и cookie-аутентификацию; маршруты с Bearer-токеном в заголовке исключены из CSRF-проверки.

Исходный код разделён на `controller`, `service`, `repository`, `dto`, `mapper`, `entity`, `exception` и `config`. Бизнес-логика находится в сервисах, API не возвращает JPA-сущности.

## CI и сдача

`.github/workflows/ci.yml` запускается на `push` и `pull_request` в GitHub. Он собирает приложение, запускает SpotBugs с Find Security Bugs (SAST) и OWASP Dependency-Check (SCA). Отчёты сканеров сохраняются как artifacts даже при ошибке проверки. Для успешного SCA-запуска нужен ключ NVD: [запросите API key](https://nvd.nist.gov/developers/request-an-api-key) и добавьте его в GitHub repository secret `NVD_API_KEY`. Для локального SCA задайте одноимённую переменную окружения и выполните `.\mvnw.cmd dependency-check:check`. Ключ не записывайте в репозиторий. Первое обновление базы NVD может занять заметное время. В текущей локальной проверке без ключа Dependency-Check не смог загрузить NVD-данные; результат SCA не получен.

Отчёт подготовлен в [`docs/report.typ`](docs/report.typ). Перед сдачей заполните ФИО, группу, ссылку на публичный репозиторий, ссылку на последний успешный запуск CI и места для скриншотов Postman/SAST/SCA. Результаты CI в отчёте пока намеренно не заявлены: они появятся после публикации репозитория.
